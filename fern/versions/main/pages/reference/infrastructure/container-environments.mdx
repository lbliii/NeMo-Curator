# Container Environments

NeMo Curator source releases continue. Starting with the 26.09 release, NVIDIA no longer publishes NeMo Curator container images to NGC. Previously published images remain downloadable.

The repository's `docker/Dockerfile` remains available for building an image from a source checkout. You can use a release tag for a released source version or the `main` branch for current development. The resulting image is your own build; tag it and publish or transfer it using the registry and container workflow available in your environment.

## Build a container

Check out a published release tag to build that released source version, or use `main` for current development. From the repository root, build and run a local image:

```bash
docker build -f docker/Dockerfile -t nemo-curator:local .

docker run --gpus all -it --rm \
  -v "$PWD:/workspace" \
  -w /workspace \
  nemo-curator:local bash
```

Inside the container, activate the virtual environment created by the Dockerfile:

```bash
source /opt/venv/env.sh
python -c "import nemo_curator; print(nemo_curator.__version__)"
```

Review `docker/Dockerfile` at the checked-out revision for the base image, optional extras, and additional components; build arguments affect the resulting image contents.

The current repository Dockerfile defaults to the `all` Curator extra, Python 3.13, CUDA 12.9.1, and Ubuntu 24.04. It installs `etcd` and `nats-server` for the Dynamo inference backend and builds the Nemotron OCR C++/CUDA extension. It does not install FFmpeg. Optional modality dependencies and external tools may differ if you change `CURATOR_EXTRA`, Dockerfile contents, or build arguments.

## Use images on a cluster

A local Docker tag such as `nemo-curator:local` is available only to the Docker daemon where it was built. Cluster jobs need an image reference or file that the cluster's container integration can access from every allocated node. For example, push the image to a registry reachable by the cluster, or export/convert it using your site's Pyxis, enroot, or other container workflow and place the resulting image file on a shared filesystem. Configure the cluster job with that registry reference or shared image path.

For SLURM examples, see [Multi-Node Ray on SLURM](/admin/deployment/slurm-multi-node-ray) and [SLURM Job Arrays](/admin/deployment/slurm-arrays). The submit scripts accept `CONTAINER_IMAGE` and pass it to the site's SLURM container plugin; they do not make a workstation-local Docker tag available to compute nodes.

## Image configuration

The current Dockerfile accepts these build-time arguments:

| Argument | Default | Description |
| --- | --- | --- |
| `CUDA_VER` | `12.9.1` | CUDA version used by the NVIDIA CUDA base image. |
| `LINUX_VER` | `ubuntu24.04` | Linux version used by the CUDA base image. |
| `CURATOR_ENV` | `ci` | Curator environment type passed into the build. |
| `CURATOR_EXTRA` | `all` | Curator optional extra installed by `uv sync`; set empty to install without an extra. |
| `CURATOR_GROUPS` | `--all-groups` | Dependency groups passed to `uv sync`. |
| `NVIDIA_BUILD_ID` | `<unknown>` | Optional build identifier label. |
| `NVIDIA_BUILD_REF` | unset | Optional build reference label. |

These defaults apply to builds using the matching Dockerfile revision and default arguments.

## Architecture notes

The Dockerfile's Python dependencies and optional extras may be architecture-gated in `pyproject.toml`. In particular, audio dependencies that require x86_64 Linux are not available on arm64 builds. Check the package constraints for the source revision and target architecture before building a workload-specific image.

Ray is the execution framework for NeMo Curator pipelines. Dask-related packages, if present in a built environment, may be transitive dependencies and are not the pipeline execution backend.
